**Status**: Complete

## Research Areas

### 1. Dependency Graph Algorithms

**Decision**: Использовать направленный ациклический граф (DAG) для представления зависимостей с алгоритмами топологической сортировки и обнаружения циклов.

**Rationale**: 
- Стандартный подход в менеджерах пакетов (npm, pip, cargo)
- Эффективное обнаружение циклических зависимостей через DFS
- Топологическая сортировка для определения порядка установки
- Поддержка множественных версий через отдельные узлы в графе

**Alternatives considered**:
- Простой список зависимостей: недостаточно для сложных сценариев
- Реляционная модель без графа: сложнее для визуализации и валидации

**Implementation approach**:
- Rust: использовать структуры данных `HashMap` и `HashSet` для графа
- Алгоритм обнаружения циклов: DFS с отслеживанием посещенных узлов
- Топологическая сортировка: Kahn's algorithm или DFS-based

### 2. Version Coexistence Strategy

**Decision**: Разрешить установку нескольких версий одной зависимости одновременно, каждая версия идентифицируется как name@version.

**Rationale**:
- Соответствует паттернам npm peer dependencies
- Позволяет разным файлам использовать разные версии без конфликтов
- Упрощает разрешение конфликтов версий

**Alternatives considered**:
- Принудительная единая версия: ограничивает гибкость, требует разрешения конфликтов
- Автоматический выбор версии: нарушает требование ручного выбора пользователем

**Implementation approach**:
- В БД: каждая версия - отдельная запись с уникальным идентификатором name@version
- В графе зависимостей: разные версии - разные узлы
- При установке: проверка доступности конкретной версии, не блокировка других версий

### 3. UI Constructor for Collection Logic

**Decision**: UI-конструктор с предопределенными условиями (чекбоксы, выпадающие списки, переключатели) без текстовых выражений.

**Rationale**:
- Простота использования для пользователей без знания синтаксиса
- Визуальная валидация условий
- Легче расширять новыми типами условий через UI
- Соответствует требованию редактируемости всех настроек через UI

**Alternatives considered**:
- Текстовые выражения: сложнее для пользователей, требует парсера
- Комбинация UI + текст: избыточная сложность для MVP

**Implementation approach**:
- Типы условий: 
  - Boolean условия (включено/выключено)
  - Условия на другие коллекции (если коллекция X активна)
  - Условия на файлы (если файл Y установлен)
  - Комбинации через AND/OR логику
- Хранение: JSON структура с типизированными условиями
- Визуализация: @xyflow/svelte для визуального редактора условий (опционально для сложных случаев)

### 4. JSON Import/Export Format

**Decision**: Единый JSON формат для всех типов (файлы, коллекции, сборки) с версионированием схемы.

**Rationale**:
- Человекочитаемый формат для отладки
- Легко парсить и валидировать
- Единый формат упрощает реализацию
- JSON широко поддерживается в Rust (serde_json) и TypeScript

**Alternatives considered**:
- YAML: более читаемый, но требует дополнительных зависимостей
- Бинарный формат: быстрее, но сложнее для отладки и совместимости
- Отдельные форматы: усложняет реализацию и использование

**Implementation approach**:
- Схема JSON:
  ```json
  {
    "version": "1.0",
    "type": "file" | "collection" | "build",
    "data": { ... }
  }
  ```
- Валидация через serde в Rust и TypeScript типы на frontend
- Версионирование схемы для обратной совместимости

### 5. Session State Persistence

**Decision**: Сохранение состояния сессии в SQLite таблице с JSON полями для сложных структур (порядок файлов, настройки UI).

**Rationale**:
- Использование существующей БД (SQLite)
- Быстрое восстановление при запуске
- Надежное хранение (транзакции БД)
- JSON поля для гибкости структуры данных

**Alternatives considered**:
- Отдельный файл: сложнее синхронизация с БД
- Только в памяти: потеря состояния при перезапуске

**Implementation approach**:
- Таблица `session_state` с полями:
  - `file_order`: JSON массив идентификаторов файлов
  - `ui_preferences`: JSON объект с настройками UI
  - `open_collections`: JSON массив ID коллекций
  - `selected_files`: JSON массив выбранных файлов
  - `recent_actions`: JSON массив последних действий
- Автосохранение при изменениях
- Восстановление при старте приложения

### 6. Batch Operations with Dependencies

**Decision**: При пакетных операциях проверять зависимости для всех выбранных файлов и показывать агрегированные предупреждения.

**Rationale**:
- Пользователь должен видеть все потенциальные проблемы перед выполнением операции
- Эффективная обработка множества файлов
- Соответствует требованию предупреждений о зависимостях

**Implementation approach**:
- Сбор всех зависимостей выбранных файлов
- Группировка предупреждений по типам (отсутствующие зависимости, конфликты версий)
- Показ сводки перед выполнением операции
- Опция "применить ко всем" для разрешения конфликтов

### 7. Drag & Drop File Reordering

**Decision**: Использовать HTML5 Drag & Drop API с сохранением порядка в session_state.

**Rationale**:
- Нативный браузерный API, хорошо поддерживается
- Интуитивный UX для пользователей
- Легко интегрировать с Svelte 5

**Implementation approach**:
- Svelte 5 обработчики `on:dragstart`, `on:dragover`, `on:drop`
- Визуальная обратная связь при перетаскивании
- Сохранение нового порядка в session_state при изменении
- Восстановление порядка из session_state при загрузке

## Technology Choices Confirmed

### Frontend
- **Svelte 5 runes**: Для реактивного состояния зависимостей и коллекций
- **@xyflow/svelte**: Для визуализации графа зависимостей (опционально)
- **Tailwind CSS**: Для стилизации компонентов управления зависимостями

### Backend
- **SQLx**: Для миграций БД и работы с зависимостями
- **serde/serde_json**: Для сериализации/десериализации JSON импорта/экспорта
- **Стандартные Rust структуры**: HashMap, HashSet для графа зависимостей
